# Issue 267: pinned dbt / Ossie reproduction

This local experiment reconstructs the scenario described in [the maintainer's
comment](https://github.com/NVIDIA/auto-ontology/issues/267#issuecomment-7148428674).
Their actual SQL fixture and manifest were not attached. The supplied fixtures
are a small, synthetic Wide World Importers-style example, not a copy of their
data or the complete Wide World Importers database.

## Inputs and execution

- Converter: `apache/ossie-converters@cb4b46b97bcdb9f2685ef2f7023b9134a4426da2`.
- Ossie document version: `0.2.0.dev0`; no version-gate changes.
- dbt converter dependencies: its own locked environment, including MetricFlow
  `0.213.0`, isolated from the application's environment. Repository dependency
  files were not changed.
- PostgreSQL 17 source: `wide_world_importers`, schema `sales`, with three views
  (`customers`, `orders`, `order_lines`) and nine columns. The application's real
  PostgreSQL connector and `ingest_catalog` populated the catalog first.
- Gateway: a local production Next.js server with actual Better Auth
  email/password login, a disposable bootstrap admin, persisted session cookie,
  real role checks, and HTTP proxying to the model import/export router. Session
  resolution and permission checks were not mocked.
- Every import used `POST /api/model/import?replace=false&embed=false`.

The source SQL, input dbt manifest, and generated Ossie document are in
[`dev_tools/fixtures/model_import`](../../dev_tools/fixtures/model_import/).
The Ossie file was generated by the pinned converter, not by rewriting native
Auto-Ontology IDs:

```sh
# Run with ossie-dbt installed from the pinned converter's locked environment.
ossie-dbt msi-to-ossie \
  -i dev_tools/fixtures/model_import/wwi_semantic_manifest.json \
  -o /tmp/wwi.ossie.yaml --model-name wwi_issue267
```

## Observed results

| Check                                                   | Baseline `a12fec75`                                                    | PR branch `10f642ba`                                               |
| ------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Real admin login                                        | HTTP 200                                                               | HTTP 200                                                           |
| Unbound converter-generated Ossie document              | HTTP 500; `psycopg.errors.UniqueViolation`, `uq_catalog_database_name` | HTTP 409; `model_import_conflict`                                  |
| Conflict report                                         | Raw backend integrity failure                                          | All 14 physical paths: database, schema, three views, nine columns |
| Mutation after rejected Ossie import                    | Not asserted for the baseline control                                  | Complete readback of all 36 DAL metadata tables unchanged          |
| Native document explicitly rebound using gateway export | HTTP 200, zero new physical nodes                                      | HTTP 200, zero new physical nodes                                  |
| New semantic objects in the fixed recovery run          | Not compared; baseline control ran afterward                           | Three terms and nine column attributes                             |
| Reimport of the fixed bound document                    | Not asserted                                                           | HTTP 200; all creation counts zero                                 |
| Anonymous gateway import                                | Not asserted                                                           | HTTP 401                                                           |

Recovery retained the rejected document after native conversion, mapped its
physical IDs by exported database/schema/table/column paths, and rewrote its
physical references (including foreign keys, joins, term representation,
attribute columns, and semantic foreign keys). Existing physical IDs were
unchanged after the successful import. The baseline control used the same local
gateway and catalog after the fixed recovery run; its unbound request still hit
the reported database-name constraint.

No production code adjustment was needed for this scenario. The existing fix
handles converted Ossie through the same preflight and transaction boundary as
native YAML.

## Automated regression

The additional PostgreSQL-backed test
`test_dbt_generated_ossie_ids_conflict_and_recover_through_export` uses the actual
generated Ossie fixture, namespaces its semantic names for isolation, and seeds
an equivalent physical catalog with different identities. It tests both
replacement modes, checks all 36 model tables after the conflict, exports target
IDs over HTTP, rebinds the original converted document, checks zero new physical
nodes, and verifies idempotent reimport. This automated test uses the backend
HTTP router; the separate live experiment above covers real gateway login and
source cataloging.

```sh
# POSTGRES_* must identify a migrated, disposable test database.
uv run --no-sync pytest auto_ontology/dal/tests/test_model_interchange.py \
  -q -k dbt_generated_ossie
```

Local result: **2 new regression cases passed**; the complete import suite
passed **127 tests**. The full backend suite with the added cases passed
**3,007 tests, with 2 live-service tests skipped**. Ruff lint/format checks passed. Fixture generation, the
baseline control, and the real authenticated gateway experiment also passed
their assertions. The checked-in generated fixture keeps routine regression
runs independent of an additional dbt installation; regeneration uses the pinned
converter environment described above.
